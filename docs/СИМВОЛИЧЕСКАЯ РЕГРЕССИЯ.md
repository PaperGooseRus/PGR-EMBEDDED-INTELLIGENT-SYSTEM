# ДОКУМЕНТАЦИЯ СИМВОЛИЧЕСКОЙ РЕГРЕССИИ
## Embedded интеллектуальная система: интерпретируемые модели параметров

**Версия:** 0.1 (черновик)
**Статус:** проектирование, код запрещён
**Область:** ядро СР для дронов, умного дома, промышленного контроля

---

## 1. НАЗНАЧЕНИЕ

Символическая регрессия (СР) находит простые интерпретируемые модели для описания параметров системы. Она:
- читает параметры и их динамику из БД;
- строит формулы, описывающие зависимости между параметрами;
- проверяет формулы на адекватность;
- публикует формулы и коэффициенты в БД;
- предоставляет интерпретируемые модели для контроля, диагностики и передачи в НС как признаки;
- остаётся масштабируемой — от MCU дрона до сервера предприятия — без переписывания ядра.

СР — простая, но интерпретируемая модель. НС её дополняет точностью, а МЦ ограничивает допустимыми переходами.

## 2. МЕСТО В СИСТЕМЕ

| Направление | Что идёт |
|---|---|
| БД → СР | Параметры, их история, категории ключей |
| МЦ → СР | Динамика переходов, оценки состояний |
| НС → СР | Остатки, значимость признаков, снимки входов/выходов |
| СР → БД | Формулы, коэффициенты, метрики качества |
| СР → НС | Простые формулы как признаки или ограничения |
| СР → Потребитель | Интерпретируемые модели для контроля и диагностики |

СР **не блокирует** горячий путь БД: работает на подписках, поиск формул — по триггеру или таймеру.

## 4. АРХИТЕКТУРА

### 4.1. Слои (снизу вверх)

1. **Модель поиска** — внешняя схема: операторы, функции, ограничения, бюджет.
2. **Источник данных** — подписка на параметры и историю.
3. **Ядро поиска** — генерация и отбор формул-кандидатов.
4. **Ядро оценки** — проверка адекватности, кросс-валидация, отбор.
5. **Публикатор** — запись формул, коэффициентов и метрик в БД.
6. **API** — запуск поиска, запрос формул, экспорт.

### 4.2. Ключевые решения

| Решение | Обоснование |
|---|---|
| Модель поиска — данные, не код | Масштабируемость между проектами |
| СР дополняет НС, а не заменяет её | Интерпретируемость + точность |
| Разделение `symreg.formulas` и `nn.feature_importance` | Контроль влияния СР на НС |
| Несколько независимых СР по namespace | Параллельные задачи без взаимного влияния |
| Гейтинг по состоянию | Экономия ресурсов в штатном режиме |
| Детерминированные вычисления | Одинаковый результат на обеих частях |

## 5. МОДЕЛЬ ПОИСКА (ВНЕШНЯЯ)

Модель — **данные, не код**. Хранится в схеме проекта, версионируется отдельно.

### 5.1. Содержимое

| Раздел | Что описывает |
|---|---|
| Operators | Допустимые операторы (`+`, `-`, `*`, `/`, `^`, ...) |
| Functions | Допустимые функции (`sin`, `cos`, `exp`, `log`, ...) |
| Constants | Допустимые константы |
| Complexity | Ограничения сложности (глубина, число узлов, число коэффициентов) |
| Targets | Целевые параметры (что описываем) |
| Features | Признаки (чем описываем) |
| Quality metric | Метрика качества (MSE, MAE, R², комбинированная) |
| Search budget | Бюджет поиска (число итераций, время, память) |
| Gating | Правила гейтинга по состоянию |
| Constraints | Дополнительные ограничения (размерность, устойчивость) |

### 5.2. Ограничения

- глубина дерева формулы ≤ 8;
- число узлов ≤ 32;
- число коэффициентов ≤ 16;
- число целевых параметров на СР ≤ 32;
- число признаков на цель ≤ 64;
- имена целей и признаков — уникальны, длина ≤ 64 байт.

### 5.3. Пример наполнения (без кода)

**Дрон:** описать `battery.soc` от `time`, `current`, `temperature`; ограничение — формула ≤ 10 узлов.

**Умный дом:** описать `climate.temp` от `time`, `heating_power`, `outside_temp`; ограничение — линейная или квадратичная модель.

**Предприятие:** описать `line.throughput` от `load`, `temperature`, `errors`; ограничение — не более 15 узлов.

**Одно ядро СР — разные модели поиска.**

## 6. СОСТОЯНИЕ-ЗАВИСИМОСТЬ

Ключевое требование. Реализуется через **гейтинг по состоянию**: в зависимости от текущего состояния МЦ и режима системы меняются сложность формул и бюджет поиска.

### 6.1. Гейтинг по состоянию

| Состояние | Сложность формул | Бюджет поиска |
|---|---|---|
| Штатное | Простые (линейные, ≤ 5 узлов) | Минимальный |
| Переходное | Средние (≤ 10 узлов) | Средний |
| Предаварийное | Полные (≤ 20 узлов) | Максимальный |
| Аварийное | Простые (устойчивые) | Минимальный |

### 6.2. Гейтинг по режиму системы

| Режим | Частота поиска | Что публикуется |
|---|---|---|
| NORMAL | Редко (по таймеру) | Формулы верхнего уровня |
| PRE_FAILURE | Часто | Полный набор формул + метрики |
| FAILOVER | Приостановлено | Только критичные формулы |
| RECOVERY | Полный пересчёт | Полный набор + сброс истории |

Правило гейтинга — часть внешней схемы. Меняется без пересборки ядра.

## 7. АЛГОРИТМ РАБОТЫ

### 7.1. Поиск формул

1. Прочитать целевые параметры и признаки из БД.
2. Определить бюджет и ограничения по текущему состоянию.
3. Сгенерировать формулы-кандидаты в допустимом пространстве.
4. Оценить каждую формулу на исторических данных.
5. Отобрать лучшие по метрике качества с учётом сложности (регуляризация).
6. Проверить на кросс-валидации.
7. Записать лучшие формулы в `symreg.formulas.*`.
8. Обновить метрики в `symreg.metrics.*`.

### 7.2. Оценка качества

- основная метрика — по схеме (MSE, MAE, R², комбинированная);
- штраф за сложность (число узлов, коэффициентов);
- штраф за неустойчивость (разброс на кросс-валидации);
- порог принятия — формула публикуется только если лучше предыдущей.

### 7.3. Проверка формул

- проверка размерности (если применимо);
- проверка допустимости операций (деление на ноль, логарифм отрицательного);
- проверка устойчивости на краях диапазона;
- проверка на соответствие ограничениям схемы.

### 7.4. Обновление формул

- формулы версионируются;
- новая формула публикуется только при улучшении метрики;
- старая формула сохраняется для отката;
- история поиска пишется в `symreg.search_log`.

## 8. РЕЖИМЫ РАБОТЫ

| Режим | Поиск | Публикация |
|---|---|---|
| NORMAL | По таймеру, простые формулы | Верхний уровень |
| PRE_FAILURE | Часто, полные формулы | Полный набор + метрики |
| FAILOVER | Приостановлено | Только критичные формулы |
| RECOVERY | Полный пересчёт | Полный набор |

Триггеры перехода — детерминированные, одинаковые на обеих частях.

## 9. ВЗАИМОДЕЙСТВИЕ С НС

СР и НС дополняют друг друга:
- НС даёт точные, но неинтерпретируемые предсказания;
- СР даёт простые, но интерпретируемые формулы;
- СР использует остатки НС для поиска неучтённых зависимостей;
- НС использует формулы СР как признаки или ограничения.

### 9.1. Схема взаимодействия

| Шаг | Действие |
|---|---|
| 1 | НС публикует предсказания и остатки |
| 2 | СР читает остатки и ищет формулы, объясняющие их |
| 3 | СР публикует формулы в `symreg.formulas.*` |
| 4 | НС читает формулы и использует их как признаки |
| 5 | СР читает значимость признаков от НС и приоритизирует поиск |

### 9.2. Правила

- СР не заменяет НС, а дополняет её;
- формулы СР не должны противоречить допустимым переходам МЦ;
- при конфликте приоритет у ограничений схемы;
- формулы с низким качеством не публикуются;
- СР не может изменять веса НС или матрицы МЦ напрямую.

## 10. ХРАНЕНИЕ В БД

Namespace `symreg.*`:

| Ключ | Что хранит | Категория |
|---|---|---|
| `symreg.targets` | Целевые параметры (из схемы) | Критическое |
| `symreg.formulas` | Найденные формулы | Операционное |
| `symreg.coefficients` | Коэффициенты формул | Операционное |
| `symreg.formulas_version` | Версия набора формул | Критическое |
| `symreg.quality` | Метрики качества формул | Операционное |
| `symreg.search_log` | Журнал поиска | Диагностическое |
| `symreg.residuals` | Остатки от формул | Диагностическое |
| `symreg.metrics` | Метрики работы СР | Локальное |

Формулы хранятся как CBOR-документы: дерево операций с коэффициентами. Это позволяет читать их на любой платформе и версионировать.

## 12. МАСШТАБИРУЕМОСТЬ

| Аспект | Как достигается |
|---|---|
| Пространство формул | Внешняя схема, разные модели на проект |
| Сложность | Бюджет и ограничения в схеме |
| Платформа | Ядро без аллокаций, фиксированные буферы |

## 13. ДЕТЕРМИНИЗМ

- Генерация формул — детерминированная (фиксированный порядок, без случайности).
- Оценка — детерминированная.
- Отбор — по детерминированному правилу (метрика + штраф + tie-break).
- Версионирование формул — по `seq`.
- При одинаковых входах основная и резервная части получают одинаковые формулы.

## 17. ТЕСТОВАЯ СТРАТЕГИЯ

### 17.1. Уровни

| Уровень | Что проверяет |
|---|---|
| Unit | Генерация формул, оценка, отбор |
| Integration | Чтение из БД, публикация результатов, подписка |
| Quality | Метрики качества, кросс-валидация, отбор |
| Mode | Переключение режимов и бюджета поиска |
| Determinism | Одинаковый результат на основной и резервной частях |
| Performance | Задержки, отсутствие аллокаций в горячем пути |
| Scalability | Работа с разными моделями поиска без пересборки |
| Interaction | Совместная работа с НС (остатки, признаки) |

### 17.2. Обязательные сценарии

- Смена состояния → корректная смена бюджета и сложности.
- Формула нарушает ограничения схемы → отклонена.
- Разрыв seq версий формул → пересинхронизация.
- Смена модели поиска → миграция формул без потери.
- Конфликт формулы с ограничениями МЦ → приоритет у схемы.
- Откат формул к предыдущей версии → корректная работа.

Тест на каждую задачу, коммит на каждую задачу. Один срез за раз.

## 18. РАЗБИЕНИЕ НА ЗАДАЧИ

**Этап 1. Модель поиска:** формат схемы → загрузка модели → тест валидации → коммит.

**Этап 2. Ядро поиска:** генерация формул → оценка → отбор → тесты → коммит.

**Этап 3. Интеграция с БД:** подписка на параметры → публикация формул → тесты → коммит.

**Этап 4. Состояние-зависимость:** гейтинг по состоянию → смена бюджета → тесты → коммит.

**Этап 5. Взаимодействие с НС:** чтение остатков → публикация формул как признаков → тесты → коммит.

**Этап 6. Экспорт:** форматы Markdown/LaTeX/текст → тесты → коммит.

**Этап 7. Порты:** MCU → Linux → сервер → тесты производительности → коммит.

## 19. ШИП

- **Шип после этапа 1:** модель поиска загружается из схемы.
- **Шип после этапа 2:** СР находит формулы.
- **Шип после этапа 3:** СР интегрирована с БД.
- **Шип после этапа 4:** СР работает в состоянии-зависимом режиме.
- **Шип после этапа 5:** СР взаимодействует с НС.
- **Шип после этапа 6:** СР экспортирует формулы для человека.
- **Шип после этапа 7:** СР работает на всех целевых платформах.
