# ДОКУМЕНТАЦИЯ БАЗЫ ДАННЫХ
## Embedded интеллектуальная система: состояние-зависимое хранилище

**Версия:** 0.1 (черновик)
**Статус:** проектирование, код запрещён
**Область:** ядро БД для дронов, умного дома, промышленного контроля

---

## 1. НАЗНАЧЕНИЕ

База данных (БД) — центральный компонент системы. Она хранит всё состояние, обслуживает марковскую цепь, нейронную сеть и символическую регрессию, а также обеспечивает обмен между основной и резервной частями.

БД — фундамент. Остальные блоки работают поверх неё.

---

## 2. МЕСТО В СИСТЕМЕ

| Направление | Что идёт |
|---|---|
| БД → МЦ | Состояние, история, категории ключей |
| БД → НС | Состояние, категории ключей, история |
| БД → СР | Параметры, история, категории ключей |
| МЦ → БД | Матрица переходов, вероятности, метрики |
| НС → БД | Веса, предсказания, корректировки, метрики |
| СР → БД | Формулы, коэффициенты, метрики |

БД не блокирует потребителей: подписка на мутации, асинхронная публикация, горячий путь без ожидания.

## 3. КЛЮЧЕВЫЕ ТРЕБОВАНИЯ

### 3.1. Функциональные

| ID | Требование |
|---|---|
| F-01 | Хранить произвольное состояние в виде ключ-значение с вложенностью |
| F-02 | Не требовать перекомпиляции под новый проект — схема внешняя |
| F-03 | Поддерживать режимы: NORMAL, PRE_FAILURE, FAILOVER, RECOVERY |
| F-04 | Реплицировать критические ключи всегда, диагностические — только в предаварии |

| F-07 | Предоставлять подписку на мутации для МЦ, НС, СР |
| F-08 | Экспортировать состояние в человекочитаемый вид (отладка) |

## 4. АРХИТЕКТУРА

### 4.1. Слои (снизу вверх)

1. **Платформа** — MCU / Linux / сервер.
2. **Персистентность** — WAL + периодические snapshots.
3. **Ядро** — generic key-value поверх CBOR-дерева.
4. **Политика** — внешний файл репликации и режимов.
5. **API** — get / set / remove / subscribe / snapshot / restore / set_mode / export.
6. **Потребители** — марковская цепь, нейронная сеть, символическая регрессия.

### 4.2. Ключевые решения

| Решение | Обоснование |
|---|---|
| Схема — данные, не код | Масштабируемость между проектами |
| Формат — CBOR | Компактно, самоописываемо, без кодогенерации |
| Ядро — generic KV | Одно на все проекты |
| Персистентность — WAL + snapshot | Атомарность, восстановление после сбоя |
| Репликация — политика, не код | Состояние-зависимость без переписывания |
| Политика — тоже данные | Меняется под проект без пересборки |

## 5. МОДЕЛЬ ДАННЫХ

### 5.1. Ключ

Строковый путь в иерархии: `namespace.field.subfield[index]`.

- Namespace = подсистема: `system`, `drone`, `home`, `enterprise`, `markov`, `nn`, `symreg`.
- Разделитель — точка.
- Индексы массивов — в квадратных скобках.
- Длина ключа ≤ 128 байт.
- Допустимы `a-z`, `0-9`, `.`, `_`, `[`, `]`.

### 5.2. Значение

CBOR-документ. Допустимые типы:
- целые (знаковые и беззнаковые);
- числа с плавающей точкой;
- булевы;
- строки (UTF-8, ≤ 512 байт);
- массивы;
- вложенные объекты;
- бинарные буферы (≤ 4 КБ).

Ограничения:
- глубина вложенности ≤ 8;
- размер значения ≤ 8 КБ;
- общее число ключей ≤ 65 536 на проект.

### 5.3. Метаданные записи

| Поле | Назначение |
|---|---|
| `seq` | Монотонный номер версии записи |
| `timestamp` | Время последней модификации |
| `source` | Кто изменил (primary/backup/local) |
| `category` | Критическое / операционное / диагностическое / локальное |
| `schema_version` | Версия схемы на момент записи |

### 5.4. Категории состояния

| Категория | Что входит | Репликация |
|---|---|---|
| Критическое | Уставки, режимы, флаги аварий, счётчики | Всегда |
| Операционное | Измерения, промежуточные результаты | Норма — редко, предавария — часто |
| Диагностическое | Логи, трассировки, гистограммы | Только в предаварии |
| Локальное | Кэш, служебные данные | Никогда |

## 6. СХЕМА (ВНЕШНЯЯ)

Схема не компилируется в бинарник. Хранится отдельным файлом, версионируется отдельно.

### 6.1. Формат описания

CDDL (RFC 8610) или JSON Schema — выбор фиксируется на этапе реализации.

### 6.2. Содержимое

| Раздел | Что описывает |
|---|---|
| Namespaces | Список пространств имён проекта |
| Keys | Перечень ключей с типами и ограничениями |
| Categories | Категория репликации для каждого ключа |
| Versions | История версий схемы и миграции |
| Validation | Правила валидации значений |

### 6.3. Пример наполнения (без кода)

**Дрон:**
- `drone.attitude` → `roll`, `pitch`, `yaw` (float, критическое);
- `drone.battery` → `v`, `i`, `soc` (float, критическое);
- `drone.diag` → `log`, `trace` (binary, диагностическое).

**Умный дом:**
- `home.climate` → `temp`, `humidity` (float, операционное);
- `home.security` → `armed`, `sensors` (bool/array, критическое).

**Предприятие:**
- `enterprise.line[N]` → `throughput`, `status` (float/int, критическое);
- `enterprise.analytics` → `histograms`, `trends` (объекты, диагностическое).

Один и тот же бинарник ядра обслуживает дрон, умный дом и предприятие. Меняется только файл схемы.

## 7. ФОРМАТ ХРАНЕНИЯ

### 7.1. Файлы на устройстве

| Файл | Назначение |
|---|---|
| `snapshot.bin` | Полный снимок состояния |
| `wal.log` | Журнал мутаций с момента последнего snapshot |
| `schema.cbor` | Схема проекта |
| `policy.cbor` | Политика репликации |
| `meta.bin` | Версия ядра, последний seq, контрольная сумма |

### 7.2. Запись WAL

Содержит:
- маркер начала;
- версию формата;
- монотонный номер (`seq`);
- тип операции (set / delete / snapshot-marker);
- ключ;
- значение (CBOR);
- контрольную сумму;
- маркер конца.

Запись атомарна: либо целиком валидна, либо игнорируется при восстановлении.

### 7.3. Snapshots

- Делаются периодически (по числу записей, времени, триггеру).
- Согласованность: copy-on-write без остановки мира.
- Хранятся минимум два последних снапшота.
- После успешного снапшота WAL обрезается до последнего seq.

### 7.4. Восстановление после сбоя

1. Загрузить последний валидный снапшот.
2. Проиграть WAL с seq > snapshot.seq.
3. Отбросить невалидные (битые) записи в хвосте.
4. Зафиксировать актуальный seq.
5. Перейти в режим NORMAL или RECOVERY.

## 8. СОСТОЯНИЕ-ЗАВИСИМАЯ РЕПЛИКАЦИЯ

### 8.1. Режимы системы

| Режим | Триггер входа | Что реплицируется |
|---|---|---|
| NORMAL | Штатная работа | Критические + heartbeat |
| PRE_FAILURE | Пороги ошибок, деградация, аварийные флаги | Критические + операционные + диагностические |
| FAILOVER | Основная часть недоступна | Резерв берёт управление |
| RECOVERY | Основная часть вернулась | Snapshot + догон дельт |

### 8.2. Детерминированность триггеров

Условия перехода, приоритеты и гистерезис вычисляются одинаково на обеих частях, иначе режимы разойдутся.

### 8.3. Политика репликации

Внешний файл `policy.cbor` содержит:
- списки критических/операционных/диагностических/локальных ключей;
- правила батчинга (сколько мутаций объединять в один кадр);
- правила подтверждения (ack) в каждом режиме.

Политика меняется без пересборки ядра.

### 8.4. Идемпотентность

- Каждая мутация имеет `seq`.
- Резерв применяет мутацию только если `seq > last_applied`.
- Повторная доставка не меняет состояние.
- Пропуск обнаруживается по разрыву `seq` → триггер RECOVERY.

## 9. ИНТЕРФЕЙСЫ С КОМПОНЕНТАМИ

### 9.1. API ядра (описание, без кода)

| Операция | Назначение |
|---|---|
| `open(path, config)` | Открыть хранилище |
| `close()` | Закрыть с корректным flush |
| `get(key)` | Прочитать значение |
| `set(key, value)` | Записать значение |
| `remove(key)` | Удалить ключ |
| `subscribe(callback)` | Подписка на мутации |
| `snapshot()` | Получить снимок |
| `restore(snapshot)` | Восстановить из снимка |
| `set_policy(policy)` | Установить политику репликации |
| `set_mode(mode)` | Переключить режим |
| `export(format, path)` | Экспорт в Markdown/CSV/JSON |

### 9.2. Марковская цепь

- Читает: текущее состояние, историю переходов.
- Пишет: матрицу переходов, вероятности, оценки.
- Подписка: на изменения ключей категории «операционное» и «критическое».
- Требование: не блокировать горячий путь БД.

### 9.3. Нейронная сеть

- Читает: состояние + вероятности переходов от марковской цепи.
- Пишет: веса, предсказания, метрики.
- Подписка: на ключи `nn.*` и на вероятности `markov.*`.
- Требование: архитектура сети описывается внешней схемой.

### 9.4. Символическая регрессия

- Читает: параметры и их динамику.
- Пишет: найденные формулы, коэффициенты.
- Подписка: на изменения параметров с историей.
- Требование: формулы хранятся как CBOR-документы, версионируются.

## 13. ТЕСТОВАЯ СТРАТЕГИЯ

### 13.1. Уровни

| Уровень | Что проверяет |
|---|---|
| Unit | Отдельные операции: get/set/remove, CBOR-кодирование, CRC |
| Integration | WAL + snapshot + восстановление после сбоя |
| Replication | Передача дельт, снапшотов, ack, разрывы seq |
| Mode | Переходы NORMAL ↔ PRE_FAILURE ↔ FAILOVER ↔ RECOVERY |
| Idempotency | Повторная доставка, переупорядочивание, дубликаты |
| Fault injection | Обрыв питания, битые записи, потеря кадров |
| Performance | Задержки, пропускная способность, износ flash |
| Portability | Сборка и запуск на MCU, Linux, сервере |

### 13.2. Обязательные сценарии

- Сбой питания во время записи WAL → восстановление без потери подтверждённых данных.
- Разрыв `seq` → автоматический переход в RECOVERY.
- Переполнение WAL → компактификация без потери состояния.
- Смена режима → корректная смена политики репликации.
- Обновление схемы → миграция без потери данных.

Тест на каждую задачу, коммит на каждую задачу. Один срез за раз.

## 14. РАЗБИЕНИЕ НА ЗАДАЧИ

**Этап 1. Фундамент:** формат WAL → формат snapshot → API → CBOR-обёртка → in-memory KV → тест → коммит.

**Этап 2. Персистентность:** WAL (append/read/replay) → восстановление после сбоя → snapshot → компактификация → тесты → коммит.

**Этап 3. Схема и политика:** формат схемы → формат политики → загрузка схемы → загрузка политики → тест валидации → коммит.

**Этап 4. Репликация:** подписка на мутации → режимы → дельты по режимам → snapshot-синхронизация → ack и seq-контроль → тесты → коммит.

**Этап 5. Интеграция:** интерфейс с марковской цепью → с нейронной сетью → с символической регрессией → тесты → коммит.

**Этап 6. Порты:** MCU (дрон) → Linux (умный дом) → сервер (предприятие) → тесты производительности → коммит.

---

## 15. ШИП

- **Шип после этапа 1:** работает in-memory KV + CBOR-обёртка. Ядро можно встраивать.
- **Шип после этапа 2:** работает персистентность. Данные выживают сбой питания.
- **Шип после этапа 3:** работает схема и политика. Ядро масштабируется между проектами.
- **Шип после этапа 4:** работает состояние-зависимая репликация.
- **Шип после этапа 5:** БД готова к интеграции с МЦ, НС, СР.
- **Шип после этапа 6:** БД работает на всех целевых платформах.

Правило: если задача не шипается — она слишком большая, режь дальше.
