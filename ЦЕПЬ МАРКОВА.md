# ДОКУМЕНТАЦИЯ МАРКОВСКОЙ ЦЕПИ
## Embedded интеллектуальная система: оценка состояний и вероятностей переходов

**Версия:** 0.1 (черновик)
**Статус:** проектирование, код запрещён
**Область:** ядро МЦ для дронов, умного дома, промышленного контроля

---

## 1. НАЗНАЧЕНИЕ

Марковская цепь (МЦ) оценивает текущее состояние системы и вероятности переходов между состояниями. Она:
- читает состояние и историю из БД;
- вычисляет вероятности переходов;
- публикует их в БД для нейронной сети и символической регрессии;
- получает от нейронной сети калибровку вероятностей;
- остаётся масштабируемой — от дрона до предприятия — без переписывания ядра.

МЦ — интерпретируемая базовая оценка. НС её уточняет, но не заменяет.

---

## 2. МЕСТО В СИСТЕМЕ

| Направление | Что идёт |
|---|---|
| БД → МЦ | Текущее состояние, история переходов, категории ключей |
| МЦ → БД | Матрица переходов, вероятности, оценки состояния, метрики |
| МЦ → НС | Вектор вероятностей, оценка текущего состояния |
| НС → МЦ | Скорректированные вероятности (калибровка), приоритеты состояний |
| МЦ → СР | Динамика переходов как параметр для описания |

МЦ **не блокирует** горячий путь БД: работает на подписках и обновляет свои ключи асинхронно.

## 4. АРХИТЕКТУРА

### 4.1. Слои (снизу вверх)

1. **Модель состояний** — внешняя схема: состояния, переходы, признаки.
2. **Источник данных** — подписка на мутации БД.
3. **Ядро оценки** — определение состояния, счётчики, сглаживание, нормализация.
4. **Калибратор** — приём корректировок от НС, применение с ограничениями.
5. **Публикатор** — запись результатов в БД.
6. **API** — запрос состояния, вероятностей, матрицы.

### 4.2. Ключевые решения

| Решение | Обоснование |
|---|---|
| Модель — данные, не код | Масштабируемость между проектами |
| МЦ не заменяется НС, а корректируется ею | Сохранение интерпретируемости |
| Разделение базовой и скорректированной матриц | Контроль влияния НС |
| Несколько независимых МЦ по namespace | Параллельные цепи без взаимного влияния |
| Работа на подписках, без блокировки БД | Не мешает горячему пути |
| Детерминированные вычисления | Одинаковый результат на обеих частях |

## 5. МОДЕЛЬ СОСТОЯНИЙ (ВНЕШНЯЯ)

Модель — **данные, не код**. Хранится в схеме проекта, версионируется отдельно.

### 5.1. Содержимое

| Раздел | Что описывает |
|---|---|
| States | Список состояний с именами и числовыми идентификаторами |
| Transitions | Матрица разрешённых рёбер (какие переходы допустимы) |
| Features | Признаки, по которым определяется текущее состояние |
| Categories | Категория каждого состояния (критическое / операционное / диагностическое) |
| Aggregation | Правила агрегации: какие ключи БД влияют на какое состояние |
| Smoothing | Метод сглаживания и его параметры |
| Gating | Правила гейтинга по режиму системы |

### 5.2. Ограничения

- число состояний ≤ 256 на МЦ;
- число признаков на состояние ≤ 32;
- число допустимых переходов ≤ 4096;
- имена состояний — уникальны, длина ≤ 32 байт.

### 5.3. Пример наполнения (без кода)

**Дрон:** состояния `idle`, `arm`, `takeoff`, `flight`, `land`, `failsafe`. Признаки — режим полёта, высота, скорость, флаги ошибок.

**Умный дом:** состояния `day`, `night`, `away`, `alarm`. Признаки — время, присутствие, датчики.

**Предприятие:** состояния `idle`, `run`, `degrade`, `stop`. Признаки — throughput, ошибки, температура.

**Одно ядро МЦ — разные модели состояний.**

## 6. АЛГОРИТМ ОЦЕНКИ

### 6.1. Определение текущего состояния

1. Прочитать признаки из БД по правилам схемы.
2. Сопоставить признаки с состояниями модели.
3. Зафиксировать текущее состояние и время входа.
4. Записать в БД (`markov.current_state`, `markov.state_since`).

### 6.2. Подсчёт переходов

Ведётся счётчик пар `(from, to)`:
- при каждой смене состояния инкрементируется соответствующая ячейка;
- счётчики хранятся в БД в namespace `markov.counts`;
- при достижении порога выполняется сглаживание и нормализация.

### 6.3. Оценка вероятностей

- базовая оценка — частоты переходов;
- сглаживание — для защиты от нулевых вероятностей (метод фиксируется в схеме);
- нормализация — сумма по строке равна 1;
- результат пишется в `markov.probabilities`.

### 6.4. Окно истории

- скользящее окно: последние N переходов;
- N зависит от режима: в NORMAL — короткое, в PRE_FAILURE — расширенное;
- старые данные вытесняются, чтобы не расти бесконечно;
- место хранения окна (БД или RAM) фиксируется в схеме.

---

## 7. РЕЖИМЫ РАБОТЫ

| Режим | Частота пересчёта | Глубина истории | Что публикуется |
|---|---|---|---|
| NORMAL | Редко (по таймеру) | Короткое окно | Текущее состояние + вероятности верхнего уровня |
| PRE_FAILURE | Часто | Расширенное окно | Полная матрица + детальные вероятности |
| FAILOVER | Приостановлено | — | Только чтение для резерва |
| RECOVERY | Полный пересчёт | Полная история | Полная матрица + сброс счётчиков |

Триггеры перехода — детерминированные, одинаковые на обеих частях.

## 8. КАЛИБРОВКА НЕЙРОННОЙ СЕТЬЮ

МЦ **не заменяется** сетью, а **корректируется** ею. Это ключевое решение: МЦ даёт интерпретируемую базовую оценку, НС уточняет её.

### 8.1. Схема взаимодействия

| Шаг | Действие |
|---|---|
| 1 | МЦ вычисляет базовую матрицу вероятностей |
| 2 | Публикует её в `markov.probabilities` |
| 3 | НС читает матрицу + состояние, вычисляет корректировки |
| 4 | НС пишет корректировки в `nn.calibration.*` |
| 5 | МЦ читает корректировки и применяет их к базовой матрице |
| 6 | Результат — скорректированная матрица в `markov.calibrated` |

### 8.2. Формат корректировок

Корректировки — CBOR-документ в БД, содержащий:
- идентификатор целевой матрицы и версию;
- тип коррекции (мультипликативная, аддитивная, замена строки);
- значения по ячейкам;
- вес доверия к коррекции (0…1);
- клиппинг (мин/макс по ячейке);
- метку времени и источник.

### 8.3. Правила применения

- коррекция применяется только если её версия новее текущей;
- вес доверия ограничивает влияние НС (защита от ошибочных коррекций);
- клиппинг ограничивает максимальное отклонение от базовой оценки;
- после применения выполняется нормализация;
- если коррекция нарушает допустимые переходы — она отклоняется;
- все применённые коррекции логируются в `markov.calibration_log`.

### 8.4. Ограничения

- НС не может обнулить допустимый переход;
- НС не может добавить недопустимый переход;
- сумма вероятностей по строке остаётся равной 1;
- при отсутствии коррекций используется базовая оценка.

### 8.5. Обратная связь

- МЦ пишет `calibration_delta` и `calibration_rejected` в метрики;
- НС читает эти метрики и корректирует вес доверия;
- при систематических отклонениях — снижение доверия к НС.

## 9. ХРАНЕНИЕ В БД

Namespace `markov.*`:

| Ключ | Что хранит | Категория |
|---|---|---|
| `markov.current_state` | Текущее состояние | Критическое |
| `markov.state_since` | Время входа в состояние | Операционное |
| `markov.states` | Список состояний (из схемы) | Критическое |
| `markov.counts` | Счётчики переходов | Операционное |
| `markov.probabilities` | Базовая матрица | Операционное |
| `markov.calibrated` | Скорректированная матрица | Операционное |
| `markov.history` | Окно последних переходов | Диагностическое |
| `markov.calibration_log` | Журнал применённых коррекций | Диагностическое |
| `markov.metrics` | Метрики работы МЦ | Локальное |

Namespace `nn.calibration.*` — корректировки от НС.

Разделение на `probabilities` и `calibrated` позволяет сравнивать базовую и скорректированную оценки и контролировать влияние НС.

## 11. МАСШТАБИРУЕМОСТЬ

| Аспект | Как достигается |
|---|---|
| Число состояний | Внешняя схема, ограничение на проект |
| Число признаков | Внешние правила агрегации |
| Платформа | Ядро без аллокаций, фиксированные буферы |
| Проект | Меняется только схема модели состояний |
| Число МЦ | Несколько независимых МЦ по namespace (`markov.drone.*`, `markov.power.*`) |

Каждая МЦ — независимый экземпляр ядра со своей моделью состояний и своим namespace. Это позволяет одной системе вести несколько цепей параллельно (полёт, питание, связь) без взаимного влияния.

## 12. ДЕТЕРМИНИЗМ

- Все вычисления — на фиксированной точке или с детерминированным округлением (выбор фиксируется в схеме).
- Порядок обновления счётчиков — детерминированный.
- Сглаживание — без случайности.
- Калибровка применяется в порядке `seq` коррекций.
- При одинаковых входах основная и резервная части получают одинаковые выходы.

## 16. ТЕСТОВАЯ СТРАТЕГИЯ

### 16.1. Уровни

| Уровень | Что проверяет |
|---|---|
| Unit | Подсчёт переходов, сглаживание, нормализация |
| Integration | Чтение из БД, запись результатов, подписка |
| Calibration | Применение коррекций, ограничения, отклонения |
| Mode | Переключение режимов и частоты пересчёта |
| Determinism | Одинаковый результат на основной и резервной частях |
| Performance | Задержки, отсутствие аллокаций |
| Scalability | Работа с разными моделями состояний без пересборки |

### 16.2. Обязательные сценарии

- Коррекция от НС нарушает допустимый переход → отклонена.
- Разрыв seq коррекций → пересинхронизация.
- Смена режима → корректная смена окна истории.
- Смена модели состояний → миграция без потери счётчиков.
- Переполнение окна истории → корректное вытеснение.

Тест на каждую задачу, коммит на каждую задачу. Один срез за раз.

## 17. РАЗБИЕНИЕ НА ЗАДАЧИ

**Этап 1. Модель состояний:** формат схемы модели → загрузка модели → тест валидации → коммит.

**Этап 2. Ядро оценки:** определение текущего состояния → счётчики переходов → сглаживание → нормализация → тесты → коммит.

**Этап 3. Интеграция с БД:** подписка на мутации → публикация результатов → тесты → коммит.

**Этап 4. Режимы:** NORMAL / PRE_FAILURE / FAILOVER / RECOVERY → смена окна → тесты → коммит.

**Этап 5. Калибровка:** формат корректировок → приём от НС → применение и ограничения → журнал → тесты → коммит.

**Этап 6. Порты:** MCU → Linux → сервер → тесты производительности → коммит.
