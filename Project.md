# ПЛАН РЕАЛИЗАЦИИ EMBEDDED ИНТЕЛЛЕКТУАЛЬНОЙ СИСТЕМЫ

## ПРИНЦИПЫ ПРОЕКТИРОВАНИЯ

1. **Документ до кода** — сначала спецификация, потом реализация;
2. **Большая задача режется на мелкие** — такие, чтобы не провалить;
3. **Один срез за раз** — не переписывать всё сразу;
4. **Тесты** — работает, докажи;
5. **Ревью** — пять осей качества перед мерджем;
6. **Шип** — быстрее значит безопаснее.

**Правило:** тест на каждую задачу, коммит на каждую задачу, шип после каждой задачи.

Каждый блок системы (БД, МЦ, НС, СР) следует этим принципам. Ниже — структура блока, единая для всех подсистем.

## ПРОЕКТИРОВАНИЕ СИСТЕМЫ

Система состоит из:
- базы данных;
- марковской цепи;
- нейронной сети;
- символической регрессии.

---

### БАЗА ДАННЫХ

#### НАЗНАЧЕНИЕ

База данных (БД) — центральный компонент системы. Она хранит всё состояние, обслуживает марковскую цепь, нейронную сеть и символическую регрессию, а также обеспечивает обмен между основной и резервной частями.

#### МЕСТО В СИСТЕМЕ

| Направление | Что идёт |
|---|---|
| БД → МЦ | Состояние, история, категории ключей |
| БД → НС | Состояние, категории ключей, история |
| БД → СР | Параметры, история, категории ключей |
| МЦ → БД | Матрица переходов, вероятности, метрики |
| НС → БД | Веса, предсказания, корректировки, метрики |
| СР → БД | Формулы, коэффициенты, метрики |

БД — фундамент. Остальные блоки работают поверх неё.

#### КЛЮЧЕВЫЕ ТРЕБОВАНИЯ

- **Состояние-зависимость.** Интенсивность обмена и репликации зависит от режима системы.
- **Масштабируемость.** Одно ядро БД работает в дронах, умном доме и на предприятии без переписывания под проект.
- **Схема — данные, не код.** Новый проект = новый внешний файл схемы, а не новая сборка ядра.
- **Атомарность.** Сбой питания не теряет подтверждённые данные.
- **Детерминизм.** Горячий путь без динамических аллокаций.
- **Портируемость.** MCU, Linux, сервер — один API.

#### АРХИТЕКТУРА

Слои (снизу вверх):

1. **Платформа** — MCU / Linux / сервер.
2. **Персистентность** — WAL + периодические snapshots.
3. **Ядро** — generic key-value поверх CBOR-дерева.
4. **Политика** — внешний файл репликации и режимов.
5. **API** — get / set / remove / subscribe / snapshot / restore / set_mode / export.
6. **Потребители** — марковская цепь, нейронная сеть, символическая регрессия.

#### МОДЕЛЬ ДАННЫХ

**Ключ** — строковый путь в иерархии: `namespace.field.subfield[index]`.
Namespace = подсистема: `system`, `drone`, `home`, `enterprise`, `markov`, `nn`, `symreg`.
Длина ключа ≤ 128 байт. Допустимы `a-z`, `0-9`, `.`, `_`, `[`, `]`.

**Значение** — CBOR-документ. Типы: целые, float, bool, строка (≤ 512 Б), массив, объект, бинарный буфер (≤ 4 КБ). Глубина вложенности ≤ 8. Размер значения ≤ 8 КБ. Общее число ключей ≤ 65 536 на проект.

**Метаданные записи:** `seq`, `timestamp`, `source`, `category`, `schema_version`.

#### КАТЕГОРИИ СОСТОЯНИЯ

| Категория | Что входит | Репликация |
|---|---|---|
| Критическое | Уставки, режимы, флаги аварий, счётчики | Всегда |
| Операционное | Измерения, промежуточные результаты | Норма — редко, предавария — часто |
| Диагностическое | Логи, трассировки, гистограммы | Только в предаварии |
| Локальное | Кэш, служебные данные | Никогда |

#### СХЕМА (ВНЕШНЯЯ)

Схема не компилируется в бинарник. Хранится отдельным файлом, версионируется отдельно.

Формат: CDDL (RFC 8610) или JSON Schema — выбор фиксируется на этапе реализации.

Содержит: namespaces, перечень ключей с типами и ограничениями, категории репликации, историю версий и миграции, правила валидации.

Один и тот же бинарник ядра обслуживает дрон, умный дом и предприятие. Меняется только файл схемы.

#### ФОРМАТ ХРАНЕНИЯ

Файлы на устройстве:

| Файл | Назначение |
|---|---|
| `snapshot.bin` | Полный снимок состояния |
| `wal.log` | Журнал мутаций с момента последнего snapshot |
| `schema.cbor` | Схема проекта |
| `policy.cbor` | Политика репликации |
| `meta.bin` | Версия ядра, последний seq, контрольная сумма |

**Запись WAL:** маркер начала, версия формата, seq, тип операции, ключ, значение (CBOR), CRC, маркер конца. Запись атомарна.

**Snapshots:** периодически по числу записей, времени или триггеру. Согласованность через copy-on-write без остановки мира. Хранятся минимум два последних снапшота. После успешного снапшота WAL обрезается.

**Восстановление после сбоя:** загрузить последний валидный snapshot → проиграть WAL с seq > snapshot.seq → отбросить битые записи в хвосте → зафиксировать seq → перейти в NORMAL или RECOVERY.

#### СОСТОЯНИЕ-ЗАВИСИМАЯ РЕПЛИКАЦИЯ

| Режим | Триггер входа | Что реплицируется |
|---|---|---|
| NORMAL | Штатная работа | Критические + heartbeat |
| PRE_FAILURE | Пороги ошибок, деградация, аварийные флаги | Критические + операционные + диагностические |
| FAILOVER | Основная часть недоступна | Резерв берёт управление |
| RECOVERY | Основная часть вернулась | Snapshot + догон дельт |

**Детерминированность триггеров.** Условия перехода, приоритеты и гистерезис вычисляются одинаково на обеих частях, иначе режимы разойдутся.

**Политика репликации** — внешний файл `policy.cbor`: списки критических/операционных/диагностических/локальных ключей, правила батчинга, правила ack в каждом режиме. Меняется без пересборки ядра.

**Идемпотентность.** Каждая мутация имеет seq. Резерв применяет её только если `seq > last_applied`. Повторная доставка не меняет состояние. Разрыв seq → триггер RECOVERY.

#### ИНТЕРФЕЙСЫ С КОМПОНЕНТАМИ

**Марковская цепь:** читает текущее состояние и историю переходов, пишет матрицу переходов и вероятности. Подписка на операционные и критические ключи. Не блокирует горячий путь БД.

**Нейронная сеть:** читает состояние и вероятности от марковской цепи, пишет веса, предсказания, метрики. Архитектура сети описывается внешней схемой.

**Символическая регрессия:** читает параметры и их динамику, пишет формулы и коэффициенты. Формулы хранятся как CBOR-документы, версионируются.

#### ВЕРСИОНИРОВАНИЕ

| Аспект | Правило |
|---|---|
| Версия схемы | `major.minor`, фиксируется в meta и каждой записи |
| Обратная совместимость | Старое ядро игнорирует неизвестные ключи |
| Прямая совместимость | Новое ядро читает старые данные через миграции |
| Миграции | Описаны в схеме, применяются при открытии БД |
| Откат | Предыдущий снапшот хранится до подтверждения миграции |
| Несовместимые изменения | Только через новый namespace |

#### МЕТРИКИ

`wal_size`, `snapshot_age`, `replication_lag`, `seq_gap_count`, `mode_transitions`, `write_latency`, `read_latency`, `flash_cycles`, `crc_errors`.

Пишутся в namespace `system.metrics`, доступны для экспорта.

#### ТЕСТОВАЯ СТРАТЕГИЯ

Уровни: unit, integration, replication, mode, idempotency, fault injection, performance, portability.

Обязательные сценарии:
- сбой питания во время записи WAL → восстановление без потери подтверждённых данных;
- разрыв seq → автоматический RECOVERY;
- переполнение WAL → компактификация без потери состояния;
- смена режима → корректная смена политики;
- обновление схемы → миграция без потери данных.

Тест на каждую задачу, коммит на каждую задачу. Один срез за раз.

#### РАЗБИЕНИЕ НА ЗАДАЧИ

**Этап 1. Фундамент:** формат WAL → формат snapshot → API → CBOR-обёртка → in-memory KV → тест → коммит.

**Этап 2. Персистентность:** WAL (append/read/replay) → восстановление после сбоя → snapshot → компактификация → тесты → коммит.

**Этап 3. Схема и политика:** формат схемы → формат политики → загрузка схемы → загрузка политики → тест валидации → коммит.

**Этап 4. Репликация:** подписка на мутации → режимы → дельты по режимам → snapshot-синхронизация → ack и seq-контроль → тесты → коммит.

**Этап 5. Интеграция:** интерфейс с марковской цепью → с нейронной сетью → с символической регрессией → тесты → коммит.

**Этап 6. Порты:** MCU (дрон) → Linux (умный дом) → сервер (предприятие) → тесты производительности → коммит.

#### ШИП

- **Шип после этапа 1:** работает in-memory KV + CBOR-обёртка. Ядро можно встраивать.
- **Шип после этапа 2:** работает персистентность. Данные выживают сбой питания.
- **Шип после этапа 3:** работает схема и политика. Ядро масштабируется между проектами.
- **Шип после этапа 4:** работает состояние-зависимая репликация.
- **Шип после этапа 5:** БД готова к интеграции с МЦ, НС, СР.
- **Шип после этапа 6:** БД работает на всех целевых платформах.

Правило: если задача не шипается — она слишком большая, режь дальше.

### МАРКОВСКАЯ ЦЕПЬ

#### НАЗНАЧЕНИЕ

Марковская цепь (МЦ) оценивает текущее состояние системы и вероятности переходов между состояниями. Она:
- читает состояние и историю из БД;
- вычисляет вероятности переходов;
- публикует их в БД для нейронной сети и символической регрессии;
- получает от нейронной сети калибровку вероятностей;
- сама остаётся масштабируемой — от дрона до предприятия — без переписывания ядра.

#### МЕСТО В СИСТЕМЕ

| Направление | Что идёт |
|---|---|
| БД → МЦ | Текущее состояние, история переходов, категории ключей |
| МЦ → БД | Матрица переходов, вероятности, оценки состояния, метрики |
| МЦ → НС | Вектор вероятностей, оценка текущего состояния |
| НС → МЦ | Скорректированные вероятности (калибровка), приоритеты состояний |
| МЦ → СР | Динамика переходов как параметр для описания |

МЦ **не блокирует** горячий путь БД: работает на подписках и обновляет свои ключи асинхронно.

#### КЛЮЧЕВЫЕ ТРЕБОВАНИЯ

- **Масштабируемость.** Одно ядро МЦ работает в дронах, умном доме и на предприятии. Различаются только модель состояний и схема.
- **Состояние-зависимость.** Частота пересчёта и глубина истории зависят от режима системы.
- **Калибруемость сетью.** Вероятности переходов корректируются нейронной сетью без пересборки ядра.
- **Детерминизм.** При одинаковых входных данных — одинаковый результат на основной и резервной частях.
- **Ограниченные ресурсы.** Работа на MCU с малым RAM.
- **Наблюдаемость.** Все матрицы, оценки и метрики доступны в БД.

#### АРХИТЕКТУРА

Слои МЦ (снизу вверх):

1. **Модель состояний** — внешняя схема, описывающая множество состояний и допустимые переходы.
2. **Источник данных** — подписка на мутации БД.
3. **Ядро оценки** — подсчёт частот переходов, сглаживание, оценка текущего состояния.
4. **Калибратор** — приём корректировок от НС, применение их к вероятностям.
5. **Публикатор** — запись результатов в БД.
6. **API** — запрос текущего состояния, вероятностей, матрицы.

#### МОДЕЛЬ СОСТОЯНИЙ (ВНЕШНЯЯ)

Модель — **данные, не код**. Хранится в схеме проекта, версионируется отдельно.

Содержит:
- список состояний с именами и числовыми идентификаторами;
- допустимые переходы (матрица разрешённых рёбер);
- признаки, по которым определяется текущее состояние;
- категорию каждого состояния (критическое / операционное / диагностическое);
- правила агрегации (какие ключи БД влияют на какое состояние).

Пример наполнения (без кода):

**Дрон:** состояния `idle`, `arm`, `takeoff`, `flight`, `land`, `failsafe`. Признаки — режим полёта, высота, скорость, флаги ошибок.

**Умный дом:** состояния `day`, `night`, `away`, `alarm`. Признаки — время, присутствие, датчики.

**Предприятие:** состояния `idle`, `run`, `degrade`, `stop`. Признаки — throughput, ошибки, температура.

**Одно ядро МЦ — разные модели состояний.**

#### АЛГОРИТМ ОЦЕНКИ

##### Определение текущего состояния

1. Прочитать признаки из БД по правилам схемы.
2. Сопоставить признаки с состояниями модели.
3. Зафиксировать текущее состояние и время входа.
4. Записать в БД (`markov.current_state`, `markov.state_since`).

##### Подсчёт переходов

Ведётся счётчик пар `(from, to)`:
- при каждой смене состояния инкрементируется соответствующая ячейка;
- счётчики хранятся в БД в namespace `markov.counts`;
- при достижении порога выполняется сглаживание и нормализация.

##### Оценка вероятностей

- базовая оценка — частоты переходов;
- сглаживание — для защиты от нулевых вероятностей (метод фиксируется в схеме);
- нормализация — сумма по строке равна 1;
- результат пишется в `markov.probabilities`.

##### Окно истории

- скользящее окно: последние N переходов;
- N зависит от режима: в NORMAL — короткое, в PRE_FAILURE — расширенное;
- старые данные вытесняются, чтобы не расти бесконечно.

#### РЕЖИМЫ РАБОТЫ

| Режим | Частота пересчёта | Глубина истории | Что публикуется |
|---|---|---|---|
| NORMAL | Редко (по таймеру) | Короткое окно | Текущее состояние + вероятности верхнего уровня |
| PRE_FAILURE | Часто | Расширенное окно | Полная матрица + детальные вероятности |
| FAILOVER | Приостановлено | — | Только чтение для резерва |
| RECOVERY | Полный пересчёт | Полная история | Полная матрица + сброс счётчиков |

Триггеры перехода — детерминированные, одинаковые на обеих частях.

#### КАЛИБРОВКА НЕЙРОННОЙ СЕТЬЮ

МЦ **не заменяется** сетью, а **корректируется** ею. Это ключевое решение: МЦ даёт интерпретируемую базовую оценку, НС уточняет её.

##### Схема взаимодействия

| Шаг | Действие |
|---|---|
| 1 | МЦ вычисляет базовую матрицу вероятностей |
| 2 | Публикует её в `markov.probabilities` |
| 3 | НС читает матрицу + состояние, вычисляет корректировки |
| 4 | НС пишет корректировки в `nn.calibration.*` |
| 5 | МЦ читает корректировки и применяет их к базовой матрице |
| 6 | Результат — скорректированная матрица в `markov.calibrated` |

##### Формат корректировок

Корректировки — CBOR-документ в БД, содержащий:
- идентификатор целевой матрицы и версию;
- тип коррекции (мультипликативная, аддитивная, замена строки);
- значения по ячейкам;
- вес доверия к коррекции (0…1);
- метку времени и источник.

##### Правила применения

- коррекция применяется только если её версия новее текущей;
- вес доверия ограничивает влияние НС (защита от ошибочных коррекций);
- после применения выполняется нормализация;
- если коррекция нарушает допустимые переходы — она отклоняется;
- все применённые коррекции логируются в `markov.calibration_log`.

##### Ограничения

- НС не может обнулить допустимый переход;
- НС не может добавить недопустимый переход;
- сумма вероятностей по строке остаётся равной 1;
- при отсутствии коррекций используется базовая оценка.

### НЕЙРОННАЯ СЕТЬ

#### НАЗНАЧЕНИЕ

Нейронная сеть (НС) — масштабируемая обучаемая модель, зависящая от состояния системы и вероятностей переходов от марковской цепи. Она:
- читает состояние системы и вероятности переходов из БД;
- вычисляет предсказания, оценки и корректировки;
- калибрует вероятности марковской цепи;
- предоставляет данные символической регрессии для построения интерпретируемых моделей;
- остаётся масштабируемой — от MCU дрона до сервера предприятия — без переписывания ядра.

#### МЕСТО В СИСТЕМЕ

| Направление | Что идёт |
|---|---|
| БД → НС | Состояние системы, категории ключей, история |
| МЦ → НС | Базовая матрица вероятностей, текущее состояние, уверенность |
| НС → БД | Веса, предсказания, метрики, эмбеддинги |
| НС → МЦ | Корректировки вероятностей (`nn.calibration.*`) |
| НС → СР | Снимки входов/выходов, значимость признаков, остатки |
| СР → НС | Простые формулы как признаки/ограничения |

НС **не блокирует** горячий путь БД: работает на подписках, инференс — по триггеру или таймеру.

#### КЛЮЧЕВЫЕ ТРЕБОВАНИЯ

- **Состояние-зависимость.** Архитектура и режим инференса зависят от текущего состояния и режима системы.
- **Масштабируемость.** Одно ядро НС работает на MCU, Linux и сервере. Различаются модель сети и точность вычислений.
- **Внешняя архитектура.** Топология сети описывается внешней схемой, не компилируется в бинарник.
- **Калибруемость МЦ.** НС выдаёт корректировки вероятностей в ограниченном виде (вес доверия, клиппинг).
- **Детерминизм.** При одинаковых входах — одинаковый выход на основной и резервной частях.
- **Ограниченные ресурсы.** Работа на MCU без динамических аллокаций в горячем пути.
- **Наблюдаемость.** Веса, предсказания, метрики и эмбеддинги доступны в БД.

#### АРХИТЕКТУРА

Слои НС (снизу вверх):

1. **Модель сети** — внешняя схема: топология, типы слоёв, активации, точность.
2. **Источник данных** — подписка на состояние и вероятности МЦ.
3. **Ядро инференса** — прямое распространение, батчирование, кэш активаций.
4. **Ядро обучения** — обновление весов (опционально, зависит от платформы).
5. **Калибратор** — формирование корректировок для МЦ с ограничениями.
6. **Публикатор** — запись весов, предсказаний и метрик в БД.
7. **API** — инференс, обучение, экспорт весов, смена режима.

#### МОДЕЛЬ СЕТИ (ВНЕШНЯЯ)

Модель — **данные, не код**. Хранится в схеме проекта, версионируется отдельно.

Содержит:
- топологию: слои, связи, размерности;
- типы слоёв (dense, conv, recurrent, attention — по доступности на платформе);
- активации;
- точность вычислений (float32 / float16 / int8 / смешанная);
- правило гейтинга по состоянию (какая подсеть активна в каком состоянии);
- ограничения на выход (клиппинг корректировок).

Пример наполнения (без кода):

**Дрон:** состояния `idle`, `arm`, `takeoff`, `flight`, `land`, `failsafe`. В `idle` — малая сеть (экономия), в `flight` — полная, в `failsafe` — ансамбль.

**Умный дом:** состояния `day`, `night`, `away`, `alarm`. В `day`/`night` — общая модель, в `away` — модель присутствия, в `alarm` — модель аномалий.

**Предприятие:** состояния `idle`, `run`, `degrade`, `stop`. В `run` — модель прогноза, в `degrade` — модель диагностики, в `stop` — модель анализа причин.

**Одно ядро НС — разные модели.**

#### СОСТОЯНИЕ-ЗАВИСИМОСТЬ

Ключевое требование. Реализуется через **гейтинг по состоянию**: в зависимости от текущего состояния МЦ и режима системы активируется та или иная подсеть или уровень точности.

##### Гейтинг по состоянию

| Состояние | Что активируется | Точность |
|---|---|---|
| Штатное | Малая подсеть / квантизованная модель | int8 / float16 |
| Переходное | Средняя подсеть | float16 |
| Предаварийное | Полная сеть или ансамбль | float32 |
| Аварийное | Модель аномалий + правила | int8 (устойчивость) |

##### Гейтинг по режиму системы

| Режим | Частота инференса | Что публикуется |
|---|---|---|
| NORMAL | Редко (по таймеру) | Предсказания верхнего уровня |
| PRE_FAILURE | Часто | Полные предсказания + корректировки МЦ |
| FAILOVER | Приостановлено | Только критичные предсказания |
| RECOVERY | Полный пересчёт | Полный набор + сброс кэшей |

Правило гейтинга — часть внешней схемы. Меняется без пересборки ядра.

#### АЛГОРИТМ РАБОТЫ

##### Инференс

1. Прочитать текущее состояние и вероятности МЦ из БД.
2. Определить активную подсеть по правилу гейтинга.
3. Подготовить входной вектор по правилам схемы (какие ключи БД идут на вход).
4. Выполнить прямое распространение.
5. Записать предсказания в `nn.predictions.*`.
6. Сформировать корректировки для МЦ и записать в `nn.calibration.*`.
7. Обновить метрики в `nn.metrics.*`.

##### Обучение

Обучение — опционально и зависит от платформы:
- **MCU:** обучение выключено, веса приходят извне.
- **Linux:** онлайн-дообучение на ограниченном окне, периодически.
- **Сервер:** полное обучение, экспорт весов на устройства.

Веса версионируются и реплицируются как критические данные.

##### Кэш активаций

- Промежуточные активации кэшируются для ускорения повторного инференса.
- Кэш ограничен по размеру и вытесняется по LRU.
- При смене состояния кэш сбрасывается.

#### РЕЖИМЫ РАБОТЫ

| Режим | Инференс | Обучение | Публикация |
|---|---|---|---|
| NORMAL | По таймеру, малая подсеть | Выключено | Верхний уровень |
| PRE_FAILURE | Часто, полная подсеть | Онлайн (Linux/сервер) | Полный набор + калибровка |
| FAILOVER | Только критичные предсказания | Выключено | Минимум |
| RECOVERY | Полный пересчёт | Полное (сервер) | Полный набор |

Триггеры перехода — детерминированные, одинаковые на обеих частях.

#### КАЛИБРОВКА МАРКОВСКОЙ ЦЕПИ

НС **корректирует** вероятности МЦ, а не заменяет их. Это сохраняет интерпретируемость и ограничивает влияние сети.

##### Схема взаимодействия

| Шаг | Действие |
|---|---|
| 1 | НС читает базовую матрицу `markov.probabilities` |
| 2 | Вычисляет корректировки на основе состояния и предсказаний |
| 3 | Применяет клиппинг и вес доверия |
| 4 | Публикует корректировки в `nn.calibration.*` |
| 5 | МЦ применяет их и пишет результат в `markov.calibrated` |

##### Формат корректировок

Корректировки — CBOR-документ в БД, содержащий:
- идентификатор целевой матрицы и версию;
- тип коррекции (мультипликативная, аддитивная, замена строки);
- значения по ячейкам;
- вес доверия (0…1);
- клиппинг (мин/макс по ячейке);
- метку времени и источник.

##### Правила формирования

- вес доверия зависит от уверенности НС и состояния;
- клиппинг ограничивает максимальное отклонение от базовой оценки;
- запрещено обнулять допустимый переход;
- запрещено добавлять недопустимый переход;
- сумма по строке нормализуется до 1.

##### Обратная связь

- МЦ пишет `calibration_delta` и `calibration_rejected` в метрики;
- НС читает эти метрики и корректирует вес доверия;
- при систематических отклонениях — снижение доверия к НС.

### СИМВОЛИЧЕСКАЯ РЕГРЕССИЯ

#### НАЗНАЧЕНИЕ

Символическая регрессия (СР) находит простые интерпретируемые модели для описания параметров системы. Она:
- читает параметры и их динамику из БД;
- строит формулы, описывающие зависимости между параметрами;
- проверяет формулы на адекватность;
- публикует формулы и коэффициенты в БД;
- предоставляет интерпретируемые модели для контроля, диагностики и передачи в НС как признаки;
- остаётся масштабируемой — от MCU дрона до сервера предприятия — без переписывания ядра.

#### МЕСТО В СИСТЕМЕ

| Направление | Что идёт |
|---|---|
| БД → СР | Параметры, их история, категории ключей |
| МЦ → СР | Динамика переходов, оценки состояний |
| НС → СР | Остатки, значимость признаков, снимки входов/выходов |
| СР → БД | Формулы, коэффициенты, метрики качества |
| СР → НС | Простые формулы как признаки или ограничения |
| СР → Потребитель | Интерпретируемые модели для контроля и диагностики |

СР **не блокирует** горячий путь БД: работает на подписках, поиск формул — по триггеру или таймеру.

#### КЛЮЧЕВЫЕ ТРЕБОВАНИЯ

- **Состояние-зависимость.** Набор формул и сложность моделей зависят от состояния системы и режима.
- **Масштабируемость.** Одно ядро СР работает на MCU, Linux и сервере. Различаются сложность формул и бюджет вычислений.
- **Внешняя модель.** Пространство допустимых формул (операторы, функции, ограничения) описывается внешней схемой.
- **Интерпретируемость.** Формулы должны быть читаемы человеком и проверяемы.
- **Детерминизм.** При одинаковых входах — одинаковый результат на основной и резервной частях.
- **Ограниченные ресурсы.** Работа на MCU без динамических аллокаций в горячем пути.
- **Наблюдаемость.** Формулы, коэффициенты, метрики качества и история поиска доступны в БД.

#### АРХИТЕКТУРА

Слои СР (снизу вверх):

1. **Модель поиска** — внешняя схема: операторы, функции, ограничения сложности, бюджет.
2. **Источник данных** — подписка на параметры и историю.
3. **Ядро поиска** — генерация и отбор формул-кандидатов.
4. **Ядро оценки** — проверка адекватности, кросс-валидация, отбор.
5. **Публикатор** — запись формул, коэффициентов и метрик в БД.
6. **API** — запуск поиска, запрос формул, экспорт.

#### МОДЕЛЬ ПОИСКА (ВНЕШНЯЯ)

Модель — **данные, не код**. Хранится в схеме проекта, версионируется отдельно.

Содержит:
- набор допустимых операторов (`+`, `-`, `*`, `/`, `^`, `sin`, `cos`, `exp`, `log`, ...);
- набор допустимых функций и констант;
- ограничения сложности (глубина дерева, число узлов, число коэффициентов);
- целевые параметры (что описываем) и признаки (чем описываем);
- метрику качества (MSE, MAE, R², комбинированная);
- бюджет поиска (число итераций, время, память);
- правила гейтинга по состоянию.

Пример наполнения (без кода):

**Дрон:** описать `battery.soc` от `time`, `current`, `temperature`; ограничение — формула ≤ 10 узлов.

**Умный дом:** описать `climate.temp` от `time`, `heating_power`, `outside_temp`; ограничение — линейная или квадратичная модель.

**Предприятие:** описать `line.throughput` от `load`, `temperature`, `errors`; ограничение — не более 15 узлов.

**Одно ядро СР — разные модели поиска.**

#### СОСТОЯНИЕ-ЗАВИСИМОСТЬ

Ключевое требование. Реализуется через **гейтинг по состоянию**: в зависимости от текущего состояния МЦ и режима системы меняются сложность формул и бюджет поиска.

##### Гейтинг по состоянию

| Состояние | Сложность формул | Бюджет поиска |
|---|---|---|
| Штатное | Простые (линейные, ≤ 5 узлов) | Минимальный |
| Переходное | Средние (≤ 10 узлов) | Средний |
| Предаварийное | Полные (≤ 20 узлов) | Максимальный |
| Аварийное | Простые (устойчивые) | Минимальный |

##### Гейтинг по режиму системы

| Режим | Частота поиска | Что публикуется |
|---|---|---|
| NORMAL | Редко (по таймеру) | Формулы верхнего уровня |
| PRE_FAILURE | Часто | Полный набор формул + метрики |
| FAILOVER | Приостановлено | Только критичные формулы |
| RECOVERY | Полный пересчёт | Полный набор + сброс истории |

Правило гейтинга — часть внешней схемы. Меняется без пересборки ядра.

#### АЛГОРИТМ РАБОТЫ

##### Поиск формул

1. Прочитать целевые параметры и признаки из БД.
2. Определить бюджет и ограничения по текущему состоянию.
3. Сгенерировать формулы-кандидаты в допустимом пространстве.
4. Оценить каждую формулу на исторических данных.
5. Отобрать лучшие по метрике качества с учётом сложности (регуляризация).
6. Проверить на кросс-валидации.
7. Записать лучшие формулы в `symreg.formulas.*`.
8. Обновить метрики в `symreg.metrics.*`.

##### Оценка качества

- основная метрика — по схеме (MSE, MAE, R², комбинированная);
- штраф за сложность (число узлов, коэффициентов);
- штраф за неустойчивость (разброс на кросс-валидации);
- порог принятия — формула публикуется только если лучше предыдущей.

##### Проверка формул

- проверка размерности (если применимо);
- проверка допустимости операций (деление на ноль, логарифм отрицательного);
- проверка устойчивости на краях диапазона;
- проверка на соответствие ограничениям схемы.

##### Обновление формул

- формулы версионируются;
- новая формула публикуется только при улучшении метрики;
- старая формула сохраняется для отката;
- история поиска пишется в `symreg.search_log`.

#### РЕЖИМЫ РАБОТЫ

| Режим | Поиск | Публикация |
|---|---|---|
| NORMAL | По таймеру, простые формулы | Верхний уровень |
| PRE_FAILURE | Часто, полные формулы | Полный набор + метрики |
| FAILOVER | Приостановлено | Только критичные формулы |
| RECOVERY | Полный пересчёт | Полный набор |

Триггеры перехода — детерминированные, одинаковые на обеих частях.

#### ВЗАИМОДЕЙСТВИЕ С НС

СР и НС дополняют друг друга:

- НС даёт точные, но неинтерпретируемые предсказания;
- СР даёт простые, но интерпретируемые формулы;
- СР использует остатки НС для поиска неучтённых зависимостей;
- НС использует формулы СР как признаки или ограничения.

##### Схема взаимодействия

| Шаг | Действие |
|---|---|
| 1 | НС публикует предсказания и остатки |
| 2 | СР читает остатки и ищет формулы, объясняющие их |
| 3 | СР публикует формулы в `symreg.formulas.*` |
| 4 | НС читает формулы и использует их как признаки |
| 5 | СР читает значимость признаков от НС и приоритизирует поиск |

##### Правила

- СР не заменяет НС, а дополняет её;
- формулы СР не должны противоречить допустимым переходам МЦ;
- при конфликте приоритет у ограничений схемы;
- формулы с низким качеством не публикуются.
